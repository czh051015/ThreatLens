## 1. 背景与目标（Why）

数据准备是多智能体闭环（采集→分析→处置→报告）的**数据基座（对应规划书 P0）**。没有真实数据，演示就是编的；用了公开数据集，演示才有可信度、可评测、可复现。当前 MVP（P1）先建**分析 Agent 内核**；采集/报告 Agent 随 MVP 一并落地；**IoC 富集 Agent** 为 P3 延后模块；**自动处置 Agent** 因安全与可演示性暂列 Non-goals（见规划书 §2）。

**本说明书只解决一件事**：把四类公开数据集取到本地、理清格式、明确它们分别喂给哪个 Agent、在评测里当什么。

原则对齐 `产品规划书.md` 的定位：

1. **规则能做的绝不用 LLM**：ATT&CK 映射走规则查表，不调模型。
2. **可评测**：Mordor 已按 ATT&CK 标注，天然可作真值；Atomic 补"已知技术链"金标。
3. **受控执行**：处置全模拟，本阶段不涉及任何真实动作。
4. **数据集是"场景来源 + 真值"，不是训练集**：本项目用规则 + 可选 LLM，不训练模型。

---

## 2. 范围（Scope & Non-goals）

**In scope（本说明书覆盖）**
- 四类数据源的选取理由、角色定位、本地落地路径。
- 已验证可用的拉取命令（含国内网络结论）。
- 归一化事件 Schema（采集 / 分析 / 评测的共同契约）。
- 确定性映射策略（ATT&CK 字典 + Sigma 桥 + LLM 仅解释层）。
- 与 Agent / 评测的映射关系、验收标准、loader 实现指引。

**Non-goals（明确不做）**
- 不训练 / 微调任何模型。
- 不接真实 EDR（个人无法获取，用 Mordor 重放 + 模拟处置替代）。
- 运行时不实时拉取外网（仅 `threatlens/core/collectors/fetch_data.py` 一次性落盘）。
- 不做自动处置（执行权不落地，延续 `product-plan.md` §7.2）。

## 3. 数据源总览与角色

| 数据集 | 在闭环里的角色 | 免费 | 当什么 |
|---|---|---|---|
| **MITRE ATT&CK STIX** | 分析 Agent 的**知识库 / 标准答案** | ✅ | 事件 → 技术（Txxxx）映射的确定性字典 |
| **Mordor / OTRF Security-Datasets** | 采集 Agent 的**真实遥测输入** | ✅ | 真实攻击 Sysmon 日志（JSONL），自带 ATT&CK 标注 |
| **Atomic Red Team** | 造攻击场景 + **评测真值** | ✅ | 可控攻击链生成器、eval 黄金标注 |
| **Sigma（必需桥）** | 遥测 → 技术的**映射规则** | ✅ | event→technique 规则，分析 Agent 的预测来源 |

> 关键定位：**ATT&CK = 技术字典（只有 name/tactic/description，无 event→technique 规则）；Sigma = 映射规则（脚本查表）；LLM = 仅解释层**。三者分工是本项目"主干脚本 + AI 三支点"工程判断的数据层落地。

## 4. 数据源详解

### 4.1 MITRE ATT&CK STIX —— 分析 Agent 的"答案书"

| 项 | 地址 |
|---|---|
| 仓库 | `https://github.com/mitre-attack/attack-stix-data` |
| 直接下载（Enterprise 最新版，约 50MB JSON） | `https://raw.githubusercontent.com/mitre-attack/attack-stix-data/master/enterprise-attack/enterprise-attack.json` |
| 锁定版本 | 同路径下 `enterprise-attack-15.1.json`（版本列表见仓库 `index.md`） |
| 官方解析库 | `pip install mitreattack-python` → `MitreAttackData("enterprise-attack.json")` |

- **结构**：STIX 2.1 bundle，`objects` 中 `type=attack-pattern` 的即技术，带 `external_references[].external_id`（如 `T1059`）、`name`、`kill_chain_phases`（战术阶段）。
- **用法**：加载为 `{technique_id: {name, tactic, description}}` 字典；分析 Agent 把遥测映射到的技术 ID 去这里取标准名称与战术，也用于版本匹配评测。
- **本地已验证**：`edr/data/attack/enterprise-attack.json` ≈ 52MB，含 **858 个 attack-pattern**，可正常 `json.load`。

### 4.2 Mordor / OTRF Security-Datasets —— 采集 Agent 的"真实案件录像"

| 项 | 地址 |
|---|---|
| 活跃仓库（**用这个**） | `https://github.com/OTRF/Security-Datasets` |
| 老仓库（已归档，别用） | `https://github.com/OTRF/mordor` |
| 单数据集直链举例（**真实路径**） | `https://raw.githubusercontent.com/OTRF/Security-Datasets/master/datasets/atomic/windows/credential_access/host/empire_mimikatz_logonpasswords.zip` |

- **格式（已实测）**：真实攻击模拟产生的 Sysmon 事件日志，**实际为 JSONL（每行一条事件）**，必须用逐行 `json.loads` 解析，不是单个 JSON 数组。字段**扁平化**——`EventID` / `EventTime` / `Hostname` / `Channel` / `Image` / `CommandLine` / `ParentImage` 直接是顶层键，**不是** Windows 事件日志的 `EventData.Image` 嵌套结构。整个数据集都标注了对应的 ATT&CK 技术。
- **本地已验证**：`edr/data/telemetry/empire_mimikatz_logonpasswords.{zip,json}`，解压后 **6026 条**真实事件，首行 `EventID=10`，顶层即含 `Hostname/Image/CommandLine`。
- ⚠️ 数据集在 `datasets/atomic/`（轻量，demo 用这个）与 `datasets/large/`（数 GB）两套；**只取 `atomic`**，别 clone 全仓。

### 4.3 Atomic Red Team —— "出题本" / 评测金标

| 项 | 地址 |
|---|---|
| 仓库 | `https://github.com/redcanaryco/atomic-red-team` |
| 结构 | `atomics/T1059/T1059.md` 按 ATT&CK 技术编号组织，1000+ 真实攻击手法 |

- **用法**：① 造一条可控攻击链（钓鱼 → 执行 → C2 → 横向 → 窃取）喂给采集 Agent；② 当评测"黄金标注"——已知用了哪些技术，验证分析 Agent 是否识别全。
- **本地已验证**：`edr/data/atomic/_src/atomics/` 下 **344 个技术目录**，每目录含 `Txxxx.md`（ATT&CK 技术原文说明，含 tactic 链接）+ `Txxxx.yaml`（可执行测试命令，如 `procdump -ma lsass.exe`）。

### 4.4 Sigma —— 遥测→技术的映射桥（必需，非可选）

- 仓库：`https://github.com/SigmaHQ/sigma`
- **为什么必需**：ATT&CK STIX 不含"EventID=1 且命令行含 powershell → T1059"这类事件到技术的映射规则。真正做 event→technique 映射的是 Sigma 规则。
- **结构（已实测）**：每条规则含 `detection:` 块（脚本查表条件）+ `tags:`（含 `attack.credential-access`、`attack.t1003.001` 等 ATT&CK 标签）。`tags` 里的 `attack.tXXXX` 直接就是技术 ID，是桥接 ATT&CK 字典的关键。
- **本地已验证**：`edr/data/sigma/_src/rules/windows/` 下 **2410 条** `.yml`。
- ⚠️ **Sigma 是映射规则 / 预测来源，不是金标**；eval 真值永远来自 Mordor 自带 ATT&CK 标注 + Atomic 链定义。

## 6. 数据格式与解析约定

| 源 | 格式 | 解析约定 |
|---|---|---|
| ATT&CK | 单个 STIX JSON bundle | `json.load` 一次性读，`objects` 过滤 `type=attack-pattern` |
| Mordor | **JSONL（每行一条事件）** | **逐行 `json.loads`**，不能整体 `json.load` |
| Mordor 字段 | **扁平化** | `EventID/EventTime/Hostname/Image/CommandLine/ParentImage` 是顶层键，映射时**不要**照抄 Windows `EventData.*` 嵌套 |
| Atomic | `Txxxx.md` + `Txxxx.yaml` | `.md` 取技术说明/战术，`.yaml` 取可执行命令（造场景用） |
| Sigma | YAML 规则 | `detection` 块为查表条件，`tags` 中 `attack.tXXXX` 为技术 ID |

## 7. 归一化事件 Schema（采集 / 分析 / 评测的共同契约）

Mordor 原始字段冗杂且命名不统一，下游（分析 Agent 映射、评测打分）必须消费统一结构。在写 `threatlens/core/data/load_telemetry.py` 前先钉死以下核心字段：

| 字段 | 类型 | 说明 | 来源（Mordor 扁平字段） |
|---|---|---|---|
| `event_id` | int | Windows 事件 ID（⚠️ 类型号非唯一 ID，见 02-分析引擎 §5.1） | `EventID` |
| `event_uid` | str | **事件唯一标识**（`数据集文件名:行号`），evidence 回溯用 | 生成（02-分析引擎 §5.1） |
| `timestamp` | datetime(UTC) | 事件时间，统一 UTC | `EventTime` |
| `host` | str | 主机名 | `Hostname` |
| `process_name` | str | 进程镜像名 | `Image` |
| `process_id` | int | 进程 PID | `ProcessId` |
| `parent_process` | str | 父进程镜像 | `ParentImage` |
| `command_line` | str | 命令行（映射关键特征） | `CommandLine` |
| `user` | str | 执行上下文用户 | `User` |
| `tactic_hint` | str \| null | 数据集自带战术提示（**仅线索，非金标**） | 数据集路径 / Mordor 标注 |
| `raw` | dict | 原始事件快照，便于回溯 | 整条原始 JSON |

**约定**：
- 所有时间统一转 UTC，字符串格式 `ISO8601`。
- `tactic_hint` 仅来自数据集级标注，是线索不是金标；金标永远是 Mordor 自带 ATT&CK 标注 + Atomic 链定义。
- 保留 `raw` 原始事件，评测争议时可回溯人工核对。
- **Schema 已由 Pydantic v2 强制校验**（见 `05-事件契约强类型化.md`）：字段类型、时间格式（ISO8601）、`event_uid` 唯一性在加载期校验，非法行抛带行号错误（fail-fast）；9050 条真实事件全量通过。
- **`event_uid` 必须生成**：`event_id` 是 Windows 事件类型号（1/10/3…），同类型事件成百上千条；evidence 引用事件一律用 `event_uid = f"{数据集文件名}:{行号}"`（见 02-分析引擎.md §5.1），**禁止**用 `event_id` 引用具体事件。

## 8. 映射策略（确定性优先）

分析 Agent 把一条归一化事件映射到 ATT&CK 技术，路径如下：

1. **Sigma 查表（确定性）**：用 Sigma 规则的 `detection` 条件匹配归一化事件字段（如 `EventID=1` 且 `CommandLine` 含 `powershell`），命中规则的 `tags: attack.tXXXX` 即为候选技术。
2. **ATT&CK 字典归一化（确定性）**：用候选技术 ID 查 ATT&CK STIX，取标准名称 / 战术 / 处理版本别名（如 `T1059.001` 归属 `T1059`）。
3. **LLM 仅解释层（可选）**：当无 Sigma 命中 / 多源冲突 / 需要自然语言解释时，才调 LLM 生成解释，**不参与判定主干**。

> 评测思路对齐 `产品规划书.md` P2：**先做确定性 baseline（Sigma 规则 + ATT&CK 字典查表，全程无 LLM），再叠可选 LLM 解释**，两版跑同一套 eval，产出对比表。真实指标（"攻击技术识别准确率""攻击链还原完整度"）写进简历是**真数**，不是编的。

## 9. 与 Agent / 评测的映射

| 数据集 | 喂给哪个环节 | 在 eval 里当什么 | 关键指标 |
|---|---|---|---|
| ATT&CK STIX | 分析 Agent（技术字典 + 映射校验） | 映射"标准答案" | 技术命中准确率、版本匹配率 |
| Mordor | 采集 Agent（真实遥测输入） | 输入真值（已知用了哪些技术） | 攻击链还原完整度 |
| Atomic Red Team | 编排器（造场景） + eval | 黄金标注 | 端到端闭环覆盖率 |
| Sigma（必需） | 分析 Agent（映射规则 / 预测来源） | 预测规则来源（非金标） | 映射召回 / 与金标比对覆盖率 |

**评测对齐方式**：Atomic 当 gold（已知技术列表），Mordor 当 realistic 输入流，两端对齐评测——把 Mordor 遥测灌入分析 Agent，看其覆盖了多少 Atomic 链定义的已知技术。

## 11. 实现指引（loader 设计）

| 模块 | 职责 | 关键实现点 |
|---|---|---|
| `threatlens/core/collectors/fetch_data.py` | 一次性拉取四源 + 校验 + 落盘 | 带重试；⚠️ msticpy 懒人法**仅限此处**一次性落盘，eval 路径禁止再调 |
| `threatlens/core/data/load_attack.py` | STIX → 技术字典 | `json.load` → 过滤 `type=attack-pattern` → `{id: {name, tactic, description}}` |
| `threatlens/core/data/load_telemetry.py` | JSONL → 归一化事件流 | **逐行 `json.loads`**；按 §7 扁平字段映射（注意 `Image` 非 `EventData.Image`，ECS 变体取 `@timestamp`/整型 `EventID`）；**生成 `event_uid`（`数据集文件名:行号`）** |
| `threatlens/core/data/load_sigma.py` | YAML 规则 → 映射表 | 解析 `detection` + `tags`，建 `{event特征: [technique_id]}` 查表 |
| `threatlens/core/data/load_atomic.py` | `Txxxx.md/.yaml` → 金标链 | 从 `_src/atomics/` 提取指定技术的说明与命令，组装评测链 |

建议首跑场景：用已下载的 mimikatz 样本（`credential_access`）打通 `threatlens/core/data/` 下 `load_attack` + `load_telemetry` + 一条 Sigma 规则查表，证明"事件 → T1003.001"链路可跑通，再扩展攻击链。

## 12. 风险与约束

| 风险 | 说明 / 缓解 |
|---|---|
| 国内网络 | `ghproxy` / `gitmirror` 镜像当前环境全失效；**用 `raw.githubusercontent.com` 直连**，或浏览器手动下载 |
| Mordor 路径易错 | 真实路径是 `datasets/atomic/...`（非过时文档里的 `datasets/small/...`），已修正 |
| JSONL vs JSON | Mordor 是逐行 JSONL，整体 `json.load` 会失败；loader 必须逐行解析 |
| 字段嵌套误判 | Mordor 字段扁平，`EventData.*` 假设不成立；按 §7 映射 |
| Sigma 当金标 | 严禁；Sigma 是预测来源，金标只能是 Mordor 标注 + Atomic 链 |
| 实时拉取污染评测 | msticpy 懒人法只允许在 `threatlens/core/collectors/fetch_data.py`，eval 只读本地 |
