## 1. 背景与目标（Why）

规划书 P2 的决策（grill Q2）是：**先跑确定性 baseline 摸底，再按 baseline 上浮定目标值，不预锁 85%/70%**。本说明书把"摸底"落成可执行的评测方案：

> 目标：用**纯规则版**（Sigma 查表 + ATT&CK 字典，全程无 LLM）跑 4 阶段 demo 链，算出**技术识别准确率（precision/recall）**和**链还原完整度**，拿到 baseline 真数字，再决定 LLM 层要不要叠、目标值定多少。

**本说明书只测 baseline，不含 LLM**——LLM 解释层是 P2 后续的可选叠加，评测方法不变（同一 AttackChain 结构、同一金标），到时可直接对比。

## 2. 范围（Scope & Non-goals）

**In scope**
- 评测口径钉死（技术识别准确率 / 链还原完整度 / 版本分离）。
- baseline 摸底跑法（官方规则版 vs 官方+自定义版）。
- 评测产物：`evaluation/metrics.json` + `evaluation/report.md`。

**Non-goals**

## 3. 评测口径（先钉死，避免算数打架）

### 3.1 金标（gold）
- 来源：`load_atomic_chain()` 从 Atomic `_src/atomics/` 提取（02 §4.6，已实现）。
- demo 链金标 4 技术：`T1059.001`（Execution）、`T1003.001`（Credential Access）、`T1087.001`（Discovery）、`T1021.002`（Lateral Movement）——即 `run_demo.py` 的 `meta.gold_techniques`。

### 3.2 技术 ID 归一化（重要，避免口径歧义）
- demo 实际识别出 `T1087`（父技术）和 `T1087.001`（子技术）同时命中。**比对前先做子技术→父技术归并**（`T1059.001→T1059`、`T1087.001→T1087`、`T1021.002→T1021`、`T1003.001→T1003`），gold 与 predicted 都归并后再算。
- 理由：ATT&CK 父/子技术同一攻击行为，分开算会人为压低指标。

### 3.3 技术识别准确率
- `predicted` = `chain.techniques` 键集（归并后）。
- `gold` = 金标技术集（归并后）。
- **precision** = |gold ∩ predicted| / |predicted|
- **recall** = |gold ∩ predicted| / |gold|

### 3.4 链还原完整度
- `gold_stages` = 金标技术的战术阶段集合（execution / credential-access / discovery / lateral-movement）。
- `predicted_stages` = `chain.chain[].tactic` 集合。
- **阶段召回** = |gold_stages ∩ predicted_stages| / |gold_stages|
- **阶段顺序一致率**（辅助指标）：predicted 链中金标阶段的相对顺序与 gold 链顺序一致的比例（两层时间线 §5.3 保证的正是这个）。

### 3.5 版本分离（02 §5.6 红线，必须遵守）
- **官方规则版**：规则集 = `_src/rules/windows/`（不含 `sigma_custom_rules/`）→ 主数字，简历写这个。
- **官方 + 自定义版**：规则集 = 官方 + `sigma_custom_rules/` → demo 链完整性数字，可提但不当主卖点。
- 两版跑同一金标、同一口径，输出对比表。**禁止只报合起来的数字**（防循环论证）。

## 5. 评测流程（跑法）

1. **取金标**：`load_atomic_chain(atomic_root, ['T1059.001','T1003.001','T1087.001','T1021.002'], attack_lib)` → gold。
2. **跑官方版**：`sigma_matcher`（规则根 = 仅 `_src/rules/windows/`）+ `chain_builder` → AttackChain A。
3. **跑官方+自定义版**：规则根 = 官方 + `sigma_custom_rules/` → AttackChain B（即现有 demo 输出）。
4. **算指标**：对 A、B 分别按 §3 口径计算，写入 `evaluation/metrics.json`。
5. **写报告**：`evaluation/report.md`——数字 + 版本对比 + 结论（LLM 有没有空间，pivot 还是续做）。

---

## 6. 预期与决策规则（Q2 pivot 逻辑）

基于 demo 现状（13 技术 vs 4 金标）的**预估**（归并前）：
- recall ≈ 100%（金标 4 技术全覆盖）。
- precision 可能偏低（~30%，13 个技术里 9 个非金标——部分是真实攻击行为非 demo 链范围，部分是规则误报）。

**决策规则（跑完按此判断）**：
| baseline 结果 | 结论 | 行动 |
|---|---|---|
| precision/recall 双高 | LLM 加不上去 | pivot 到"可解释性/冲突推理/证据链"叙事 |
| recall 高、precision 低 | **LLM 空间在"降噪/去误报"** | LLM 解释层定位为"低分证据复核"，主叙事不变 |
| recall 低 | 规则覆盖不足 | 优先扩规则（补 demo 阶段），再谈 LLM |

> 注：预估仅供参考，**以实际跑出数字为准**；本阶段不预锁 85/70（Q2 决策）。

## 8. 风险与约束

| 风险 | 说明 / 缓解 |
|---|---|
| precision 低吓到自己 | 正常——baseline 摸底的目的就是看到真实数字；pivot 规则（§6）已预设 |
| 金标粒度 | Atomic 按子技术目录组织，父级技术（如 T1087 无目录）会跳过 → 金标统一用小粒度 ID（§3.2 已处理） |
| 归并掩盖问题 | 归并只用于指标计算，报告里同时附原始明细，避免"看起来都对" |
| 版本分离被忽略 | §3.5 红线，metrics.json 强制两套数字同出 |
